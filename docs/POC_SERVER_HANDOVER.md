# 기존 PoC 서버 인수 (#8)

담당은 김시연이며, 기존 도쿄 서버의 배포·상태 확인·복구 절차를 인수한다. 기능 수정은 정민(Bedrock #104), 유진(음성 #96), 선영(화면 #105) 담당이다. 일정·권한·범위·비용 결정은 민준 담당이다.

## PoC 직접 배포 결과 (11/24)

PR107 최신 커밋의 재승인·CI 통과를 확인한 뒤 `dev`에 Squash merge했다(`4899e4c`). `dev → main` 배포 PR110을 생성했으나, 이후 사용자의 명시적인 PoC 직접 배포 지시에 따라 해당 dev 버전을 기존 서버에 적용했다. PR110은 미병합이며 main은 변경하지 않았다. GitHub 보호·리뷰 설정을 변경하거나 우회 병합하지 않았다.

배포 이미지의 기능 소스는 `1f77eb4`다. `4899e4c`와 src·scripts·data·public·의존성·Next/Docker/Compose 설정이 같고 인수 문서만 다름을 확인했다. web·voice만 준비한 이미지로 교체했으며 gateway 컨테이너와 기존 엔진 설정은 유지했다. 이전 이미지·설정 백업을 검증하고 전환 직전 설정도 비공개로 보존했다.

- 테스트 주소: `https://13.193.31.177/realtime-poc`.
- HTTPS 200과 실제 브라우저의 Haiku 표시·대화 시작 버튼을 확인했다. 이 화면 표시만으로 모델 성공을 판정하지 않았다.
- voice 모듈 로딩과 내부 상태 확인을 통과했다. 별도로 배포된 voice 컨테이너에서 고정 문구로 Haiku 5.5를 한 번 호출해 실제 요청·응답 성공을 확인했다. 사람의 질문이나 대화 원문을 사용하지 않았다.
- WSS 무인증 연결은 거부됐고, 기존 서버 키로 서명한 짧은 수명의 시험 JWT는 ping/pong을 통과했다. 키·JWT·비밀 설정을 기록에 노출하지 않았다. SDK는 무인증 소켓을 종료하므로 특정 HTTP 401 응답만을 요구하지 않았다.
- web·voice·gateway가 실행 중이고 재시작 횟수는 0이었다. gateway의 컨테이너 ID·시작 시각은 전환 전과 같았다.
- 실제 복구 실행, 사람의 마이크 입력→답변 검사→음성 출력 전체 경로, 끼어들기·발화 앞부분 잘림·모바일 시작/종료·한국어 음질 평가는 미확인이다. 게임·CUDA/GPU 검증은 수행하지 않았다.

민준/유진의 PC 마이크·끼어들기 재시험과 선영의 모바일 시작·종료 확인 후 결과를 수합한다. 모델 단건 성공을 실제 음성 시험 완료로 처리하지 않으며 #8과 #89 전체를 완료 처리하지 않는다. 아래의 배포 전 기록은 각 시점의 이력이다.

## Haiku 5.5 통합과 배포 준비 (11/24)

정민의 PR106 `49a1066` 변경만 가져와 `1f77eb4`로 따로 커밋했다. 도쿄의 `jp.anthropic.claude-haiku-5-5` 추론 프로필과 `maxTokens: 1000`, temperature 미전달을 유지한다. 원격 CI 전체 통과, 실제 서버의 web·voice 이미지 빌드와 기존 Compose 결합 대조를 완료했다. 준비 결과와 미확인 범위는 [통합 인수 안내](../ops/voice-poc/README.md#haiku-55-통합-준비-1124)에 기록했다.

운영본과 백업은 보존된 상태다. 새 커밋으로 PR107의 GitHub 재승인이 필요하며, 사용자는 재승인·dev→main 배포 절차를 따르기로 선택했다. 실제 배포·엔진 변경·Haiku 실호출·실제 음성 시험은 아직 하지 않았다. 아래 이전 기록의 미확인 항목은 각 확인 시점 기준이며, 이번 준비가 PoC 완료를 뜻하지 않는다.

## 11/24 PR107 수정 요청 반영

추가 재검토에서 첫 SDK 연결이 끝나기 전 화면을 이탈·복귀하면 이전 연결의 비동기 종료와 새 연결이 겹칠 수 있음을 확인했다. 종료 중인 Promise를 보존하고 새 시작은 그 완료 후에만 마이크·토큰·SDK 연결을 진행하도록 보완했다. 첫 연결 핸들 반환과 `endSession`을 각각 지연시킨 경우, 종료 완료 전에 새 연결이 생기지 않는지와 대기 중 취소도 다루는 회귀 검사를 추가했다. 실제 장치에서의 확인은 별도로 남는다.

민준의 11/22 리뷰에 따라 BFCache로 돌아온 화면에서 수동 대화를 다시 시작하도록 `pageshow`를 처리하고, 이전 세션의 늦은 콜백은 기존 epoch로 계속 차단했다. 빈 음성 인식에도 현재 질문의 빈 응답 종료를 보내며, 답변 생성기 오류는 원문을 노출하지 않고 실패 상태만 기록한 뒤 SDK가 해당 질문의 종료 신호를 보내도록 반복을 마무리한다.

화면 이탈·복귀 중 SDK import가 대기 중인 경우와 연결된 경우, 같은 WebSocket 세션에서 빈 인식·첫 조각 전 오류·일부 출력 후 오류 다음에 정상 질문을 처리하는 회귀 검사를 추가했다. 로컬에서는 문법·ESLint·CPU TypeScript 정적 확인만 수행하며 이 검사나 실제 마이크·Haiku 대화는 실행하지 않았다. 변경 커밋의 원격 CI와 담당자 재검토는 PR에서 별도로 확인한다. 게임·CUDA/GPU 검증도 수행하지 않았다.

## 11/19 브라우저 SSH에서 직접 확인한 내용

11/24에는 기존 서버의 이미지·설정·운영 소스 백업과 정확한 이미지 ID에 고정한 복구 Compose를 준비했다. 서버 내부 백업 경로·실제 확인 결과·한계는 [통합 인수 안내](../ops/voice-poc/README.md#1124-백업과-복구-준비-결과)에 기록했다. 과거의 "백업을 수행하지 않았다"는 문장은 11/19 조회 당시 기록이다. 실제 배포·복구 실행·엔진 변경은 여전히 수행하지 않았다.

Codex 내장 브라우저에서 IAM 로그인 후 도쿄 Lightsail의 `sejong-voice-poc-tokyo`에 브라우저 SSH로 접속했다. `ubuntu`의 일반 Docker 접근은 권한 오류가 나므로 조회는 `sudo docker`로 수행했다. Docker 그룹·방화벽·SSH 설정은 변경하지 않았다.

| 대상 | 실행 이미지 | Compose 프로젝트 | 구성 파일 |
| --- | --- | --- | --- |
| `sejong-poc-web-1` | `sejong-poc-web:20261113` | `sejong-poc` | `/opt/sejong-poc-ops/voice-compose.yaml` |
| `sejong-poc-voice-1` | `sejong-poc-voice:20261114` | `sejong-poc` | `/opt/sejong-poc-ops/voice-compose.yaml` |
| `sejong-poc-public-gateway-1` | `caddy:2.11.9` | `sejong-poc-public` | `/opt/sejong-poc-ops/compose.yaml` |

- 세 컨테이너는 조회 당시 실행 중이었다. Compose 작업 디렉터리는 `/opt/sejong-poc-ops`다. web·voice의 컨테이너 작업 디렉터리는 `/app`이며 호스트 소스를 마운트하지 않는다.
- gateway는 Caddy의 config/data Docker 볼륨, `/etc/letsencrypt`, `/var/lib/sejong-acme`, 운영 `Caddyfile`과 `routes.caddy`를 마운트한다. 운영 보완을 새 저장소 구성으로 덮어쓰지 않는다.
- 비밀 환경 파일은 `/opt/sejong-poc-ops/private/web.env`, `voice.env`, `gateway.env`다. 경로와 컨테이너 환경 변수 이름만 조회했고 비밀값은 출력하지 않았다.
- voice에는 현재 `REALTIME_POC_ANSWER_MODULE`이 없고, 실행 환경 변수 이름에 AWS 인증 변수도 없다. 현재 고정 답변 서버와 Haiku 연결 배포를 구분해야 한다.
- `/opt/sejong-voice-poc/.env.runtime`에는 `AWS_BEARER_TOKEN_BEDROCK` 이름이 존재한다. 값·유효성·현재 SDK와의 인증 호환성은 확인하지 않았다. API 호출은 하지 않았다.
- 운영 소스 후보는 `/opt/sejong-voice-poc/releases/20261113-connect`다. 이 Git 저장소의 HEAD는 `3ebd170b2e8b8b17403bfd5490ffc49b31c4cec8`이며 미커밋·미추적 보완이 있다. `/opt/sejong-voice-poc` 자체는 Git 저장소가 아니다. 이 소스와 실제 이미지의 파일 일치 여부는 추가 대조가 필요하다.
- 추적 파일 보완: `docs/REALTIME_POC_SPEECH_ENGINE.md`, `next.config.ts`, `scripts/realtime-poc/create-engine.mjs`, `scripts/realtime-poc/speech-engine-server.mjs`, `src/features/chat/sample-turn.ts`, `src/features/realtime-voice/use-speech-engine-voice.ts`.
- 미추적 보완: `.dockerignore`, `ops/`, `src/app/realtime-poc/`, `src/features/chat/realtime-poc.tsx`, `tests/speech-engine-hook-race.test.mjs`. 서버 밖의 별도 로컬 보완본 위치는 아직 미확인이다.
- 기존 `ops/voice-poc/Dockerfile`의 voice 단계는 `scripts/realtime-poc`만 복사하고 기본 Node 명령으로 실행한다. PR106은 `src`·`data`와 `--conditions=react-server`가 필요하므로 기존 이미지 태그만 바꿔서 연결 완료로 처리할 수 없다.
- 운영 `create-engine.mjs`에는 공급자 오류 원문 대신 고정 오류 분류/HTTP 상태만 기록하는 보완이 있다. PR97의 새 파일로 단순 덮어써 이 보완을 잃지 않도록 한다.

### 통합 후보와 배포 전 남은 조건

`feat/8-poc-server-handover`에 PR97 `0e8fdc109d22d666cf4ea5c67cef7d6e05e83171`과 PR106 `df366795bf8c948f766c1df84cabc47c3c03a377`을 통합 후보로 반영했다. 두 PR의 의존성·잠금 파일과 환경 예시를 합쳤으며 다른 공급자·버전을 추가하지 않았다. 운영 소스의 공개 가능한 변경 11개를 브라우저 SSH로 수집하고 SHA-256을 대조한 뒤 통합했다. 원본 묶음은 로컬 private에 보존하고 파일별 지문·기준 커밋은 `ops/voice-poc/operating-source-lock.json`에 기록했다. 이 후보를 현재 운영본이나 배포 완료로 간주하지 않는다.

운영 훅·로그 보호·standalone/worker 설정·샘플 질문 별칭은 보존했다. 실제 음성 화면은 그대로 가져오되, 고정 답변/Haiku 표시를 배포 설정에 맞추도록 했다. voice Docker 단계에는 PR106의 소스·자료와 Node 조건을 추가했으며, 기존 Compose를 덮어쓰지 않는 추가 파일과 적용/복구 절차를 [통합 인수 안내](../ops/voice-poc/README.md)에 정리했다.

### PR 준비에서 수행한 확인

- 고정 의존성을 `npm ci --ignore-scripts`로 설치했다. 전체 공개 코드 ESLint, Node 구문, Next route 타입 생성과 CPU TypeScript noEmit, 공백 검사는 통과했다. 로컬 private의 원본 자료·다른 worktree는 검사 대상에서 제외했다.
- 운영 원본 4개 파일(Next 설정·WS 서버·샘플 질문·음성 훅)과 엔진 오류 로그 보호 부분이 통합본에 그대로 남았음을 정적으로 대조했다.
- 패키지와 잠금 파일의 루트 의존성이 일치하고, 운영 원본 manifest에 11개 파일 지문이 있음을 확인했다.
- Compose 추가 파일은 Windows에 없는 Linux 환경 파일 경로만 로컬 빈 fixture로 대체해 정적 파싱을 확인했다. 실제 운영 base Compose와의 결합·비밀 환경·Docker 이미지 빌드는 확인하지 않았다.
- 가져온 훅 경합 검사에서 SDK 준비 이벤트를 PR97 규격에 맞춰 보완하고, 실제 준비 신호 전 연결 상태 유지 사례를 추가했다. 로컬 테스트·모의 앱·모델/API·실제 음성·게임·CUDA/GPU 실행은 하지 않았다. GitHub CI 결과는 PR의 실제 커밋과 함께 별도로 확인한다.

1. 현재 이미지 ID·소스·비밀 설정 경로를 기준으로 독립된 복구 자료를 확보한다. 이번 조회에서는 백업·태그 변경도 수행하지 않았다.
2. 이 PR에 보존한 운영 소스 외에 서버 밖 보완본이 더 있는지 기존 운영자에게 확인한다. 소스와 실제 실행 이미지의 파일 일치 여부도 확인한다. 기존 훅의 종료/경합 처리, 실제 화면 연결, 서버 로그 보호를 보존한다.
3. 운영 빌드·실행 구성에 PR106의 소스/자료 복사·Node 조건·답변 모듈 지정과 기존 Bedrock 인증 주입 방법을 맞춘다. 인증값은 기존 서버 비밀 설정에 둔다.
4. PR97의 ASR 키워드는 엔진 설정 갱신이 별도로 필요하다. 기존 엔진 설정·인증·음성·호출 제한을 먼저 대조하고 변경 범위를 정한다. 기존 엔진을 미리보기 설정으로 통째로 덮어쓰지 않는다.
5. #8 PR의 담당자 검토와 승인 절차 후 기존 Compose 프로젝트를 사용해 배포하고, 상태·복구 방법과 실제 배포 버전을 기록한다. 이후 유진 PC·선영 모바일 시험 결과를 수합한다.

11/17부터 웹 공통 Basic 로그인은 제거된 상태로 유지한다. 공급자 JWT·TLS·WSS·기존 통화 제한은 보존한다. 이번 브라우저 작업은 운영 정보 조회뿐이며 재시작·설정 변경·엔진 갱신·배포·모델/API 호출은 하지 않았다.

## 먼저 받을 인수 정보

민준에게 아래의 **위치와 방법**을 받는다. 비밀번호·키·전체 환경 파일은 이슈·PR·채팅에 첨부하지 않는다. 필요한 비밀값은 팀의 기존 비공개 전달 방식으로 인수한다.

- 서버 SSH 사용자명·포트·접속 방법, 사용할 키의 안전한 전달/로컬 보관 방법, 최초 접속 시 대조할 호스트 키 지문과 필요한 권한.
- 실제 운영 소스 경로와 서버 밖 보완본 위치, 변경 파일 목록, 각각의 운영 반영 여부.
- 현재 배포 명령과 실행 디렉터리, Compose 프로젝트명·서비스명·추가 파일·프로필·환경 파일 **경로**, 기존 실행 옵션.
- web·voice·gateway 이미지 식별자, 네트워크·영구 볼륨 연결과 직전 정상 버전의 보관 위치.
- HTTPS·WSS 인증, 통화 제한, 인증서 갱신을 관리하는 구성 위치와 상태 확인 방법.
- 기존 상태 확인·장애 대응·복구 절차와 이미 수행한 시험의 버전·결과 링크.

접속 정보가 없으면 이 단계에서 대기한다. 새 서버·엔진·계정·키를 만들거나 다른 서버용 키를 임의로 적용하지 않는다.

## 접속 후 읽기 전용으로 확인할 순서

아래는 운영자가 사용할 **조회 예시이며 이번 인수 준비에서 실행하지 않았다**. 먼저 인수받은 호스트와 SSH 호스트 키 지문을 대조한다. 호스트 키 검증을 끄지 않는다. 권한 부족은 필요한 권한만 요청한다.

```sh
# 경로와 도구의 존재만 확인한다. 파일 내용을 출력하지 않는다.
test -f /opt/sejong-poc-ops/voice-compose.yaml
test -f /opt/sejong-poc-ops/compose.yaml
docker compose version

# 전체 환경 설정 대신 실행 중인 프로젝트·서비스·이미지만 조회한다.
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Label "com.docker.compose.project"}}\t{{.Label "com.docker.compose.service"}}'
```

서비스명과 컨테이너를 식별한 뒤 아래의 `<container>`를 실제 이름으로 바꾼다. 종료된 컨테이너도 복구 대상으로 확인해야 하면 기존 운영자의 안내에 따라 확인한다.

```sh
# 전체 inspect에는 비밀 환경 변수가 포함될 수 있으므로 필요한 필드만 조회한다.
docker inspect --format '{{.Name}} imageId={{.Image}} imageRef={{.Config.Image}} status={{.State.Status}} restartCount={{.RestartCount}}' <container>
docker inspect --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{println}}{{end}}' <container>
```

공개 문서에는 이미지 ID·서비스 역할·필요한 경로만 정리한다. 전체 `docker inspect`, `docker compose config`, 환경 파일, 원문 로그를 그대로 게시하지 않는다. 필요한 오류 기록은 키·토큰·사용자 대화 원문을 제외해 기록한다.

Compose 조회도 인수받은 **기존 프로젝트명·실행 디렉터리·옵션**을 그대로 사용한다. 파일 경로만 보고 새로운 프로젝트명으로 실행하지 않는다. `up`, `down`, `restart`, `pull`, `build`, 최초 설치 스크립트는 읽기 조회가 아니므로 이 단계에 포함하지 않는다.

### 실제 운영본과 로컬 보완본 대조

1. Compose의 build context 또는 이미지 출처를 확인하고, 실제 소스 경로·빌드 시점·커밋을 확인한다. 컨테이너 이미지와 Git HEAD가 같다고 가정하지 않는다.
2. 소스 경로가 확인된 뒤 해당 저장소의 `git rev-parse HEAD`, `git status --short`, `git diff --name-status`로 변경 **목록**부터 확인한다. Git 저장소가 아니면 그 사실을 기록한다.
3. 서버 밖 보완본도 같은 방식으로 목록을 확인하고, 비밀 파일을 제외한 실행 코드·설정 예시만 대조한다. 민감한 변경 내용을 통째로 출력하거나 전체 폴더를 Git에 추가하지 않는다.
4. 아래 표에 운영 반영 여부와 담당자를 적는다. 정민·유진·선영의 기능 코드를 인수 과정에서 대신 구현하지 않는다. 공개 가능한 운영 보완을 저장소에 옮길 경우 #8의 실제 diff로 검토할 수 있게 한다.

| 구성/보완 | 소스 경로·확인 버전 | 운영 이미지 ID | 미커밋/별도 변경 | 운영 반영 여부 | 담당·후속 PR |
| --- | --- | --- | --- | --- | --- |

| voice / 고정 답변 | 미확인 | 미확인 | 미확인 | 미확인 | 시연 인수, 유진 기능 확인 |

## 배포 전 확보할 복구 자료

- 변경 전 web·voice·gateway 이미지 ID와 다시 사용할 수 있는 이미지 태그/보관 방법을 확보한다. 변경 전 이미지가 없어질 수 있는 prune은 하지 않는다.
- 기존 Compose 프로젝트명·실행 옵션·파일 버전·비밀 설정의 안전한 보관 위치를 기록한다. 현재 파일만 남겨두고 이를 이전 설정의 백업이라고 간주하지 않는다.
- 인증서·인증·통화 제한·네트워크와 영구 볼륨 연결을 확인한다. 기존 세션의 메모리 상태는 재시작 시 사라질 수 있다.
- 저장소의 기존 사용량 원장은 `USAGE_DB_PATH`를 사용하며 기본값은 `private/usage/ledger.sqlite`다. 운영에서 이 원장을 사용하는지는 별도 확인한다. 사용 중인 SQLite 및 `-wal`/`-shm` 파일을 임의 복사·삭제하지 않는다. 운영 저장 방식에 맞는 일관된 백업 방법을 확인한다.
- 배포 실패 시 원래 이미지·설정으로 돌아가는 명령과 복구 확인 방법을 기존 운영자에게 받아 기록한다. 미확인 명령을 실행 가능한 배포/복구 절차로 확정하지 않는다.

## 연결본 배포와 확인

현재는 프로젝트명·서비스명·이미지 보관 방법이 미확인이므로 **확정된 배포·복구 명령은 아직 없다**. 아래 정보를 확보한 후 기존 운영 절차의 실제 명령을 이 문서에 추가한다. `main`이나 `dev`를 현재 운영본 위에 바로 덮어쓰지 않는다.

| 기록할 항목 | 현재 상태 |
| --- | --- |
| 배포 작업 디렉터리·Compose 프로젝트/서비스·기존 옵션 | 미확인 |
| 배포할 PR·커밋·운영 보완 포함 여부 | 미확인 |
| 변경 전 이미지·설정의 안전한 복구 위치 | 미확인 |
| 기존 배포 명령·영향받는 서비스 | 미확인 |
| 실패 시 복구 명령·확인 방법 | 미확인 |
| 배포 후 상태 확인 방법과 실제 결과 | 미확인 |

배포 준비가 갖춰지면 관련 담당자의 기술 리뷰와 기존 승인 절차를 따른다. 새 공급자·요금제·권한 확대는 이 인수 작업에 포함하지 않는다.

배포 후에는 기존 인증이 유지되는지, web·voice·gateway 상태와 HTTPS/WSS 경로가 정상인지 확인한다. 저장소의 앱은 `APP_ORIGIN`과 단일 상시 Node 프로세스를 전제로 하므로 기존 설정·구조를 임의 변경하지 않는다. 별도 상태 확인 URL이 있는지는 운영 구성에서 확인하며, 확인하지 않은 health endpoint를 만들어 사용하지 않는다.

유진에게 시험 주소와 **실제 배포 버전**, 고정 답변/Haiku 연결 여부를 전달한다. 유진의 마이크·끼어들기·종료 결과와 선영의 화면·모바일 결과를 #85에 연결한 뒤 #89의 기존 10문항 평가를 진행한다. 서버 단건 호출·합성 음성 왕복·모의 검사·사람의 실제 대화 결과를 각각 구분한다.
