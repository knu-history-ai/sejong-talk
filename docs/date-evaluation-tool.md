# 날짜 평가도구 사용 안내

현재 본실험 기준은 [구조화 날짜 자동 평가와 독립 표본 검증](date-automatic-sample.md)입니다. 전체 53문항×5방법의 구조화 날짜를 코드로 평가하고, 실행 전에 날짜 유형을 균형 있게 고정한 12문항×5방법·60개 예정 출력 중 완료 출력을 시연·선영이 각각 독립 검증합니다. 민준은 준비·배포·수합·이견 정리 진행·분석·논문 작성을 맡고 독립 첫 판정에는 참여하지 않습니다. 유진은 실행·기록·전체 폴더/오류 전달만 맡습니다. 시연의 추가 답변 검증 수락은 #71 자료 검수 수락과 별개이며 아직 미확인이고, 선영은 10/16 중 진행을 수락했습니다. 아래 예비시험·전체 사람 최종 채점 안내는 기존(legacy) 경로로 보존합니다. 기존 `packets / import-review / finalize / report / validate-judge`의 전수 판정·이견·출처 검증 요건은 유지하며, 표본 검증을 전체 사람 채점 완료로 바꾸지 않습니다. 필수 JSON의 `date-methods-v5-structured` 실행과 이전 선택적 JSON 실행은 같은 조건의 비교로 섞지 않습니다.

관련 이슈: [#62](https://github.com/knu-history-ai/sejong-talk/issues/62).
이 도구는 MODEL 경로에서 자료와 질문을 직접 넣는 예비시험·비교 실험용입니다.
앱의 사료 등록·출처 표시와 음성 인식률을 시험하는 도구는 아닙니다.
#56 앱 통합시험과 #57 자료·앱 연결 업무는 그대로 진행합니다.

## V·T 포함 실행본과 기존 전체 사람 채점 경로(legacy)

V·T 구현은 [V·T 계약과 검증](date-vt-methods.md)을 따릅니다. 기본 예비시험 명령은 기존 R/P/E 3방식을 유지합니다. 본실험 준비 명령은 R/P/E/T/V 5방식을 모두 고정합니다. 유진님이 방법·설정·채점 옵션을 선택하지 않습니다.

검수 승인 후 **설정 담당자**가 아래 명령을 실행합니다. 경로는 실제 파일에 맞춰 담당자가 지정하며, 유진님께 이 명령을 맡기지 않습니다. 로컬 모델이 없다면 `--model-identity "고정_모델정보.json"`으로 기존 실험의 모델 식별 정보를 가져올 수 있습니다. 실제 실행 시 설치된 모델 정보가 일치하는지 다시 검사합니다.

```sh
node "./scripts/prepare-date-main.mjs" --dataset "검수된 모델입력.json" --gold "검수된 정답표.json" --private-dir "담당자 전용" --out "유진님 실행폴더"
```

`final / approved`와 검수자 기록이 없으면 본실험 폴더를 만들지 않습니다. 실제 검수 전에 표시만 바꾸면 안 됩니다. 담당자 전용 `plan.json`에는 정답이 있습니다. 전달용은 `export-operator`로 따로 만들어 정답표와 예비 정답이 든 `pilot.mjs`를 제외합니다. 두 계획은 같은 ID·자료/정답/설정 해시로 연결되므로 결과를 다시 생성할 필요가 없습니다.

유진님은 전달받은 폴더에서 `node "./run-evaluation.mjs"`만 실행하고 전체 폴더를 돌려줍니다. 반환된 `run.json`을 담당자 전용 폴더에 `import-run --dir "담당자 전용" --file "돌려받은 폴더/run.json"`으로 등록합니다. 새 본실험 준비 명령은 실행 전에 표본을 자동 고정하고 정답 없는 실행 폴더를 내보내며, 이후 자동 평가·표본 검증은 [새 기준](date-automatic-sample.md)의 순서를 따릅니다. 아래 전체 독립 최종 채점 절차는 legacy 경로입니다. 실패나 중단 확인·자료/정답 수정·내용 채점은 유진님 업무가 아닙니다.

## 기존 전수 사람 채점 경로의 역할(legacy)

아래는 예비시험·전수 사람 평가 경로의 역할 설명입니다. 현재 본실험 담당·수락 상태는 문서 첫머리와 [현재 실행 안내](date-automatic-sample.md)를 따릅니다.

- 유진님: 준비된 실행 명령을 실행하고 답변 원문·환경·오류 기록을 전달합니다. 앱 동작 확인은 #56대로 별도로 합니다. 자료·설정·정답표를 편집하거나 내용 점수를 매기지 않습니다.
- 구현·채점 담당: 계획과 기준을 준비하고 코드 검사·AI 예비 채점·사람 채점·집계를 진행합니다.
- 최종 채점자 두 명: 다른 사람이나 AI의 판정을 보기 전에 각자 판정합니다. 차이가 나면 원문과 고정 정답표를 보고 이유를 남겨 확정합니다. 실제 담당자는 별도로 협의해야 합니다.

현재 기본 자료는 시연님이 준비한 S1~S3와 B01~B08입니다. 질문 원문을 바꾸지 않았습니다.
정답표는 기존 답안 기준을 구조화한 초안이며, 기본 상태는 `pilot / draft`입니다.
코드 검증을 통과했다고 사료 독립 검토·실제 오류 확인·AI 채점기 검증·논문 실험이 끝난 것은 아닙니다.

```sh
node "./scripts/run-date-pilot.mjs"
```

이 명령은 Q4_K_M 양자화를 확인하고 실제 모델 파일 정보를 고정한 뒤, 같은 사료 3개·질문 8개를 기본·규칙·근거 우선 방식으로 실행합니다. 모델을 사용하는 두 방식은 모두 `think: false`로 실행합니다. 준비 호출을 포함해 모델 호출은 25회이며 준비 호출은 비교 비용과 분리합니다. 예비시험이므로 논문의 최종 성적표로 사용하지 않습니다.

완료되면 `evals/sejong/date-eval/results/yujin-pilot` 폴더 전체를 압축해 담당자에게 전달합니다. 오류·중단도 같은 폴더와 터미널 오류를 그대로 전달합니다. 폴더가 이미 있으면 재실행하지 않습니다. 자료·모델 설정 변경, 채점과 집계는 담당자가 진행합니다. 모델이나 양자화가 다르면 임의로 바꾸지 말고 오류와 `ollama list` 결과를 전달합니다.

### 담당자가 준비한 평가 폴더를 받은 경우

Node.js 24와 지정된 Ollama 모델은 담당자가 미리 준비합니다.
담당자가 준비한 평가 폴더를 받으면 **그 평가 폴더에서 터미널을 열고** 아래 명령만 실행해 주세요.

```sh
node "./run-evaluation.mjs"
```

폴더에 실행 코드가 함께 들어 있어 저장소 설치·npm 명령이나 준비한 사람의 컴퓨터 경로가 필요하지 않습니다.
공백·한글이 있는 경로나 다른 위치로 옮겨도 명령은 같습니다. 폴더 이름을 바꾸거나 압축해 옮길 때도 파일을 일부만 빼지 말고 전체 폴더를 유지합니다.
`operator.json`과 `실행안내.md`에도 같은 명령이 적혀 있습니다.

실행이 끝나면 `run.json`, `progress.json`, `operator.json`, `generation-calls`를 포함한 **평가 폴더 전체**를 담당자에게 전달합니다.
`run.json`에는 전체 실제 입력·답변, 단계별 호출·오류·재시도·시간·토큰, 컴퓨터 환경이 남습니다.
채점 칸을 작성할 필요는 없습니다. 모델 설치·설정 문제가 있으면 오류를 그대로 전달합니다.
실행 중 프로그램이 끊겨 실제 호출 상태를 확인할 수 없으면 자동 재실행하지 않고 담당자 확인을 요구합니다.
`generation-calls`에는 준비 호출·중간 추출·최종 답변·실패·재시도를 호출별로 저장합니다.
각 호출 전에 입력을 저장하고, 응답이나 오류를 받은 즉시 원출력·확인된 토큰·처리 시간을 저장합니다.
최종 답변 중 프로그램이 종료돼도 이전에 완료된 호출 기록은 남습니다. 끝나지 않은 호출은 `in-flight`로 보존하며 완료나 비용 0으로 추정하지 않습니다.
기록을 저장하지 못하면 모델 호출 실패로 꾸미거나 자동 재시도하지 않고 실행을 중단합니다.
이미 완료된 실행은 덮어쓰지 않습니다.

## 담당자가 먼저 준비할 것

아래의 모델 이름은 예시입니다. 실제 설치된 Qwen3.5 4B Q4 모델 태그와 양자화 정보를 확인해 사용합니다.
유료 API는 사용하지 않으며, 로컬 Ollama 주소만 허용합니다.

```sh
npm run eval:date -- prepare --dir evals/sejong/date-eval/results/pilot-before --model qwen3.5:4b --repeats 1 --warmup
```

준비 시 자료·질문·정답·채점 기준·방법 구현·모델 옵션을 해시로 고정합니다.
새 계획은 `think: false`를 실행 조건으로 고정하며 준비·추출·답변·AI 예비 채점 요청의 최상위 필드로 전달합니다. `options` 안에 넣지 않습니다. thinking 설정이 없는 과거 실행을 새 실행과 같은 조건으로 간주하지 않습니다. 이번 변경 전 준비한 폴더는 그대로 덮어쓰지 말고 새 계획으로 준비합니다.
모델을 호출하는 계획은 준비 시 Ollama 모델 조회 또는 담당자가 보존한 `--model-identity` 파일이 필요합니다. 모델 파일 해시와 양자화 정보를 함께 고정하고 실행 전에 다시 확인합니다.
prepare는 `plan.json`, `operator.json`, `실행안내.md`, `run-evaluation.mjs`, `execution-code`를 같은 폴더에 만듭니다.
이 준비 폴더에는 정답표가 있으므로 담당자가 보관합니다. `export-operator --dir "준비 폴더" --out "전달용 새 폴더"`로 실행 전용 폴더를 따로 만들어 전달합니다. 실행 코드는 준비 당시 버전으로 고정되어 경로가 바뀌어도 작동합니다.
유진님 컴퓨터에서도 지정 모델·양자화가 같고 계획에 적힌 로컬 Ollama 주소가 사용 가능한지 담당자가 먼저 확인합니다.
이전 버전으로 준비해 실행 파일이 없는 폴더는 담당자가 새로 prepare합니다. 유진님이 경로·계획·기준을 고칠 필요는 없습니다.
세 방법을 같은 질문·반복 횟수로 실행합니다.

| 방법 | 처리 |
|---|---|
| prompt-baseline | 날짜 구분·날짜 보존·근거 요구를 포함한 강화 프롬프트, 모델 1회 |
| rule-baseline | 대상 사건과 본문 구절의 날짜를 찾는 규칙 방식, 모델 호출 없음 |
| evidence-first | 같은 모델로 사건별 시간 근거를 먼저 추출하고, 그 결과를 원문과 대조해 정밀도를 제한하는 답변 프롬프트, 모델 2회 |

규칙이나 AI가 정답표를 보고 답을 생성하지 않습니다. 정답표는 채점 단계에만 들어갑니다.
규칙 방식도 틀릴 수 있으며, 본문의 새로운 사건 표현을 모두 이해하는 완성된 날짜 해석기가 아닙니다.
evidence-first도 답변의 정확성을 보장하지 않습니다. 추가 호출을 포함한 방법 전체의 정확도·비용을 비교합니다.
모델을 사용하는 방법의 생성 옵션·문맥 길이는 같습니다. 각 문항은 대화 이력 없이 새로 실행합니다.
`--timeout 120000 --retries 0`이 기본입니다. 재시도 횟수는 결과를 보기 전에 고정합니다.

별도 옵션은 JSON 파일을 `--options 옵션.json`으로 넣습니다. 기본값은 temperature 0, seed 62, num_ctx 8192, num_predict 1024입니다.
준비 후 코드를 바꾸면 기존 계획으로 새 호출을 실행할 수 없습니다. 새 폴더에 새 계획을 준비합니다.
준비용 호출은 본 비교 시간·토큰과 분리됩니다. 배치 실행 순서는 seed로 고정됩니다.
중간에 멈췄다가 완료된 항목을 건너뛰어 재개한 경우도 표시합니다. 재개 시 준비 호출은 다시 하며, 실제 경과 시간은 이번 구간만 남으므로 완전한 배치 시간이나 효율 개선으로 해석하지 않습니다.

최종 자료로 확대할 때는 담당자가 `--dataset 자료.json --gold 정답.json`을 함께 지정합니다.
기사·사건 묶음으로 개발/최종 자료를 분리하고, 정답표의 날짜 정밀도·생략 허용 범위·근거 위치·지표 적용 여부를 독립 검토해야 합니다.
기본 3기사·8질문만으로 일반적인 개선 효과를 주장하면 안 됩니다.

## 채점 순서

### 1. 코드 검사

```sh
npm run eval:date -- code --dir evals/sejong/date-eval/results/pilot-before
```

`code.json`은 구조화된 날짜 값·필수 요소·인용 위치를 검사합니다.
답변 전체가 JSON이거나 JSON 코드블록 하나인 경우를 같은 기준으로 읽습니다. 언어 표시가 없는 코드블록과 `json`/`JSON`, Windows 줄바꿈도 허용합니다.
바깥 코드블록만 채점할 때 임시로 벗기며 답변 원문·해시·인용 위치는 바꾸지 않습니다. 앞뒤 설명에서 JSON을 골라내거나 잘못된 JSON을 자동으로 고치지는 않습니다.
자연어 답변을 숫자만 보고 최종 정답으로 판정하지 않습니다.
정확한 위치에 있는 인용도 답의 의미를 뒷받침하는지는 사람이 판단합니다.
형식 검사 실패는 모델 실행 실패나 최종 내용 0점으로 바꾸지 않습니다.

### 2. AI 예비 채점

```sh
npm run eval:date -- ai --dir evals/sejong/date-eval/results/pilot-before --model 설치된-로컬-채점모델
```

`ai.json`에 입력·원출력·채점기 모델/옵션/프롬프트 해시·재시도·별도 비용이 남습니다.
AI 채점 결과의 JSON 코드블록도 같은 방식으로 읽고, 보존한 원출력으로 판정을 재검증할 때도 같은 형식 처리를 적용합니다.
`ai-calls`에도 호출 전 입력과 종료/실패 원문을 바로 저장합니다. AI 채점 중 끊기면 실행 시작 기록을 보존하며 같은 폴더에서 무작정 다시 호출하지 않습니다.
한 답변씩 원문·질문·고정 정답표와 비교하며 생성 방법·생성 옵션은 숨깁니다.
유효한 날짜 판정과 실패한 근거 판정은 분리합니다.
전체 호출 실패·시간초과·전체 해석 불가이면 해당 출력의 모든 대상 판정을 실패로 둡니다.
AI 예비 판정은 최종 점수가 아니며 사람 검토자에게 먼저 보여주지 않습니다.

### 3. 두 사람의 독립 최종 채점

```sh
npm run eval:date -- packets --dir evals/sejong/date-eval/results/pilot-before
```

검토자에게 `review-share` 폴더만 따로 전달합니다.
`review-private.json`, `plan.json`, `code.json`, `ai.json`, 다른 검토자의 판정은 전달하지 않습니다.
익명·무작위 순서의 질문·자료·정답 기준·실제 답변과 빈 판정 양식이 제공됩니다.

각자 `blank-review.json`을 복사해 다음을 채웁니다.

- `reviewerId`: 두 사람의 서로 다른 ID
- `independent / blind`: 독립·익명 검토를 실제로 했으면 true
- 문항 `date / evidence`: 날짜·근거 각각 0 또는 1, 판단 못 했으면 null
- 사건별 `date`: 각 사건의 날짜 점수
- 사건별 오류: `unsupportedDay` 일자 단정, `missingKnownDay` 알려진 일자 누락, `headerConfusion` 표제일 혼동. 오류 있으면 1, 없으면 0. 적용 대상이 아닌 항목은 null
- `reason`과 사건별 `reasons`: 실제 답변·원문을 보고 판정한 이유
- `elapsedMs`: 선택 입력. 해당 항목의 실제 검토 시간. 없으면 null이며 0초로 계산하지 않음

`eligibility`를 보고 적용 대상을 확인합니다. 필수 사건을 답변이 빠뜨렸어도 그 사건의 채점 칸을 삭제하지 않습니다.
질문 날짜 점수는 모든 필수 사건을 맞혀야 1입니다. 날짜가 맞아도 근거가 빠지거나 틀리면 근거 0입니다.
부정 전제 거절과 근거 없는 날짜 부정은 정답 기준대로 구분합니다.

```sh
npm run eval:date -- import-review --dir evals/sejong/date-eval/results/pilot-before --file 검토A.json --reviewer 검토A
npm run eval:date -- import-review --dir evals/sejong/date-eval/results/pilot-before --file 검토B.json --reviewer 검토B
npm run eval:date -- finalize --dir evals/sejong/date-eval/results/pilot-before
```

첫 판정 파일은 덮어쓰지 못합니다. 두 사람의 첫 점수·합의 전 일치 수/전체 수·이견을 보존합니다.
한 번에 전부 제출하지 않아도 됩니다. 같은 검토자 ID로 미제출 항목만 담은 JSON 배열을 추가 등록하세요.
등록할 때마다 별도 파일을 저장하며 이전 파일은 그대로 둡니다. 이미 제출한 항목을 다시 보내면 전체 등록을 거절하므로 새 항목만 보내세요.
이견이나 보류가 있으면 `final.json`의 `agreement.details`를 보고 별도 합의 JSON 배열을 준비합니다.
각 합의에는 packetId, packetHash, 두 reviewerIds, 원래 firstReviewHashes, 확정 점수·사건별 판정·이유를 넣습니다.
필요하면 합의 시간 elapsedMs도 남깁니다. 원래 첫 판정은 바꾸지 않습니다.

```sh
npm run eval:date -- finalize --dir evals/sejong/date-eval/results/pilot-before --adjudications 합의.json --out evals/sejong/date-eval/results/pilot-before/final-resolved.json
npm run eval:date -- report --dir evals/sejong/date-eval/results/pilot-before --final evals/sejong/date-eval/results/pilot-before/final-resolved.json
```

미실행·상태 미확인·미채점·미해결 이견은 0점으로 메우거나 버리지 않고 최종 집계를 막습니다.
생성 실패는 최종 0점이지만, 시간초과 부분 답변을 사람이 내용 채점하지 않습니다.
모든 질문의 실행이 실패로 확정되면 사람 채점 대상은 0개입니다. 담당자는 `packets` 실행 후 사람 판정을 등록하지 않고 `finalize` → `report`를 실행합니다. 날짜·근거 점수와 완료율은 0으로 집계되고, 완료 답변만의 정확도는 대상이 없어 N/A로 남습니다. 완료 답변의 사람 판정이 빠졌거나 실행 상태가 미확인이면 최종 보고서는 만들지 않습니다. 유진님은 이 경우에도 실행 기록과 폴더를 전달하기만 하면 됩니다.
잘못된 답변·의미 있는 답변 거절·읽을 수 있는 형식 오류는 완료 답변으로 채점합니다.
길이 제한에 걸린 답변은 먼저 상태 미확인으로 남깁니다. 도구는 자연어의 읽을 수 있는 정도를 완벽하게 자동 판정하지 않습니다.
담당자가 중단 여부와 원출력을 확인해 완료/실패를 확정합니다. 시간초과로 확정된 실패는 부분 내용이 맞아도 완료로 바꿀 수 없습니다.
정상 종료했어도 의미 없는 중단 답변으로 확인되면 내용 채점 전에 실패로 정리합니다.

상태 확인 JSON은 `[{"recordId":"원본 ID","originalRecordHash":"원본 기록의 SHA256","reviewerId":"담당자","state":"failed","reason":"중단 답변이라 읽을 수 없음","evidence":"원문과 종료 로그 대조"}]` 형식입니다.
담당자가 도구의 canonical SHA256 `hash(record)`로 원본 해시를 확인합니다.

```sh
npm run eval:date -- resolve-state --dir evals/sejong/date-eval/results/pilot-before --file 상태확인.json --out evals/sejong/date-eval/results/pilot-before/run-resolved.json
```

원본 `run.json`은 보존됩니다. 이후 code·ai·packets·import-review·finalize·report·validate-judge 명령에 `--run evals/sejong/date-eval/results/pilot-before/run-resolved.json`을 똑같이 붙입니다.
기존 채점 파일을 만든 뒤 상태를 변경했다면 이전 결과는 덮어쓰지 말고 새 폴더에서 확인본을 가져와 다시 채점합니다.
보고서를 만들기 전에 코드·AI 채점 비용이 같은 계획·기준·실행 기록의 것인지 확인합니다.
하나라도 다르면 보고서와 비용 파일을 만들지 않습니다. 채점을 실행하지 않아 비용 파일이 없으면 비용은 null로 남기며 0으로 추정하지 않습니다.
`evaluation-cost.json`에는 실행 기록 해시와 사용한 코드·AI 채점 파일의 해시도 남깁니다.
비용에 음수·문자열·잘못된 호출 수·서로 맞지 않는 토큰 분모/합계가 있으면 보고서 생성을 막습니다. 사람 채점 시간도 음수나 문자열이면 거절합니다.

AI 채점 도중 프로그램이 끊겨도 담당자는 사람 최종 채점을 마친 뒤 보고서를 만들 수 있습니다.
`aiExecution.status`는 미실행 `not-started`, 완료 `completed`, 중단 `interrupted`를 구분합니다.
중단 상태에서는 `ai-start.json`과 `ai-calls`의 출처를 확인하고 완료·실패 호출에서 확인된 입력/출력 토큰의 `partialKnownSum`과 처리 시간의 `partialKnownElapsedMs`를 집계합니다.
호출이 진행 중이면 전체 호출 수·토큰 총합은 null로 남기고 기록된 시도 수·종료 확인 수·미확인 호출 수를 따로 표시합니다.
부분 처리 시간은 호출별 시간의 합이며 전체 AI 채점 작업의 경과 시간은 아닙니다. 전체 경과 시간은 null로 유지합니다.
시작 기록 없이 호출 기록만 있거나 출처·비용 값이 맞지 않으면 집계를 막습니다. 중단된 호출을 자동 재실행하지 않습니다.
호출 번호가 빠졌거나 호출 기록에 계획/실행/시작 해시가 없으면 출처를 확인할 수 없으므로 자동 집계하지 않습니다. 구형 기록도 해시를 임의로 보충하지 말고 담당자가 별도로 확인합니다.
이 확인과 집계는 채점 담당의 일이며 유진님에게 추가로 맡기지 않습니다.

## AI 채점기 검증

AI를 조정하는 기사·사건 묶음과 검증하는 묶음을 분리한 JSON 파일을 준비합니다.
예: `{"calibrationGroups":["S1"],"validationGroups":["S2","S3"]}`.
현재 자료만으로 충분한 검증 표본이 되는 것은 아닙니다. 모든 방법·오류 유형을 포함한 실제 답변을 추가해야 합니다.
고친 채점기를 이전에 검증에 쓴 자료만으로 재검증하지 않습니다.

```sh
npm run eval:date -- validate-judge --dir evals/sejong/date-eval/results/pilot-before --groups 검증그룹.json --final evals/sejong/date-eval/results/pilot-before/final-resolved.json
```

`judge-validation.json`에는 날짜·근거·사건 오류별 사람 0/1 × AI 0/1/실패 표와 방법별·유형별 결과가 나옵니다.
유형별 집계는 고정 정답표의 `category`를 우선 사용합니다. 이 값이 없는 기존 자료는 입력 자료의 `type`을 사용하고, 둘 다 없으면 `unspecified`로 묶습니다. `category`가 있으면 공백이 아닌 문자열이어야 합니다. 이 분류는 집계에만 쓰며 모델 생성·AI 채점 입력이나 사람 채점지에는 추가하지 않습니다.
저장된 AI 점수를 보존된 원출력에서 다시 재구성해 대조합니다. 점수만 수정한 파일은 검증에 쓸 수 없습니다.
전체 일치율에는 AI 실패를 포함하고, 유효 판정 내 일치율과 채점 완료율을 따로 냅니다.
AI를 신뢰해도 모든 완료 답변의 사람 최종 채점은 생략하지 않습니다.

## 개선 전후 비교

개선 후에는 새 폴더를 사용하되 동일한 자료·정답·기준·모델 옵션·실행 조건을 사용합니다.
방법 구현을 고칠 경우 버전과 코드 해시가 달라지는 것을 남깁니다.
방법을 수정하면 `runner.mjs`의 `METHOD_VERSION`도 올립니다. 같은 버전 이름에 다른 구현을 숨기면 전후 비교를 거절합니다. 다만 보고서 파일만 바뀐 경우는 아래의 확인된 호환 규칙을 적용합니다.
채점 기준을 바꿨다면 전후 답변을 새 기준으로 모두 다시 채점해야 합니다.

```sh
npm run eval:date -- compare --before evals/sejong/date-eval/results/pilot-before/report.json --after evals/sejong/date-eval/results/pilot-after/report.json --out evals/sejong/date-eval/results/before-after.json
```

각 `report.json`에서 방법별 결과를 보고, `comparison.json`에서 한 실행 안의 고정된 방법들을 비교합니다. 본실험은 R/P/E/T/V 5방식입니다.

#62 기준으로 새 보고서(`metricVersion: 2`)는 대표·보조 지표를 다음과 같이 구분합니다.

- 대표값 `methods[].primary`: 전체 사건 문항 최종 정답률이며 `core.accuracy`와 같습니다. 실행 실패도 0점으로 고정 분모에 포함하고 표제일 대조 문항은 제외합니다.
- 보조값 `methods[].supplementary.articleEqualWeight`: 문항별 반복 평균 → 기사별 문항 평균 → 기사 동일 가중 평균입니다. 기사마다 질문 수가 다르면 대표값과 달라질 수 있습니다.
- 지표 이름과 대표값의 출처는 `metricDefinitions`에 기록합니다. 완료 후 정확도·완료율·오류·근거·비용 기준은 바꾸지 않습니다.

기존 보고서는 수정하거나 덮어쓰지 않습니다. `metricVersion`이 없는 이전 보고서의 `primary`는 기사 동일 가중 평균입니다. 이를 새 대표값으로 읽지 말고, 이전 결과의 문항 기준 정답률은 `core.accuracy`에서 확인합니다. 비교 도구는 각 버전의 집계값을 따로 검증하고 원래 문항별 판정으로 비교하며 입력 파일은 바꾸지 않습니다. 비교 결과의 `sourceMetricVersions`로 구·신 버전을 구분합니다. 같은 원본으로 새 보고서를 만들려면 기존 실행·최종 판정을 별도 담당자 폴더에 보존해 가져온 뒤 생성하며, 답변 모델을 다시 실행하거나 기존 보고서 값을 수동으로 고치지 않습니다. 이 작업은 채점·도구 담당이 맡고 유진님은 실행·기록·폴더 전달만 맡습니다.

보고서 파일만 바뀌어 전체 코드 해시가 달라진 실행도, 나머지 7개 모듈의 내용과 방법 버전이 같다고 확인되면 비교할 수 있습니다. 현재 확인된 과거 버전은 `ad4c93a`와 `7905e8c`의 고정 소스 해시이며, 현재 비교 도구의 실제 소스도 대조합니다. 확인하지 않은 과거 해시는 자동 허용하지 않습니다. 향후 새 버전을 과거 버전으로 비교하려면 도구 담당이 원래 소스를 확인해 호환 목록에 추가해야 합니다. 보고서가 호환된다고 적어 놓은 값만 믿고 통과시키지 않습니다.

허용한 비교의 방법·원래 전체 해시·보고서를 제외한 코드 지문은 `implementationCompatibility`에 남깁니다. 자료·정답표·설정·예정 문항·채점 집계 검사는 그대로 유지합니다. 실행과 실행 폴더 내보내기는 여전히 준비 당시 전체 코드 해시가 일치해야 합니다. 이전 폴더의 코드를 교체하거나 실행·계획·최종 판정 해시를 고쳐 맞추지 않습니다. Windows에서도 새로 받는 평가 모듈의 줄바꿈을 LF로 고정합니다. 이 호환 확인과 보고서 생성도 도구 담당 업무이며 유진님에게 추가 작업을 맡기지 않습니다.
전후 보고서는 질문·반복 단위로 개선, 새 오답, 둘 다 정답, 둘 다 0점을 비교합니다.
보고서에 해시로 고정된 자료·질문 목록을 함께 보존합니다. 양쪽에서 같은 문항이나 반복을 빼도 원래 예정 목록과 대조해 비교를 거절합니다.
기사 구분과 집계값도 원래 목록·기록으로 재확인합니다. 이 목록이 없는 이전 버전 보고서는 그대로 비교하지 말고 기존 실행·최종 판정 원본으로 새 보고서를 만듭니다.
‘둘 다 0점’에는 생성 실패와 완료 오답도 포함됩니다. 둘 다 완료한 경우만 따로 보는 보조 결과도 있습니다.
반복 실행은 독립 질문 수로 세지 않습니다. 질문 평균 → 기사 평균 → 기사 동일 가중 평균을 제공합니다.

핵심 사건 질문과 표제일 대조 질문, 전체 실행의 분모를 분리합니다.
정답률·조건부 정답률·완료율·오류율은 분자·분모와 함께 저장됩니다.
완료 답변의 중앙값/p95와 실패·재시도를 포함한 전체 처리 비용을 구분합니다.
모델 호출·토큰 누락은 N/A와 확인된 부분합으로 남기며, 코드·AI·사람 채점 비용은 `evaluation-cost.json`으로 분리합니다.
다른 모델/옵션을 섞은 전후 보고서는 기본 비교에서 거절합니다. 모델 자체를 바꾸는 실험은 별도 비교 조건을 먼저 설계해야 합니다.

#56 기존 기록을 재사용하려면 담당자가 같은 자료·조건·전체 원문을 갖췄는지 확인해 이 도구의 Run 형식으로 연결합니다.
`import-run --dir 준비폴더 --file 기존-run.json`은 고정 ID·버전·전체 입력을 검사하며 모델을 재호출하지 않습니다.
실제 요청의 모델·옵션도 고정 계획과 대조합니다. 상태 미확인 기록도 실제 입력이 있어야 하며, 입력 없이 완료로 바꿀 수 없습니다.
예전 기록에 없던 입력·시간·비용을 추측해서 보충하지 않습니다.

## 구현 검증과 남은 확인

```sh
npm run test:date
```

모의 생성·모의 사람 판정과 로컬 HTTP 모의 서버로 상태·산술·전체 명령 흐름을 검증합니다.
실제 Qwen 답변·실제 AI 판정 정확도·사람 검토자의 독립성은 자동 테스트가 증명하지 않습니다.
도구는 `paperEligible: false`로 두며, 데이터 검토 상태와 논문 준비 완료를 혼동하지 않습니다.
실제 오류 확인, 연구 진행 판단, 독립 사료 검토, 개발/최종 자료 확보, 채점 담당 확정, 실제 채점기 검증은 별도로 남겨야 합니다.

### 전체 흐름 점검 범위

| 단계 | 자동 검사·재현 범위 |
|---|---|
| prepare | 자료/정답/설정 해시, 질문·사건·방법 중복/누락, 빈 대상 사건, 잘못된 명령 옵션 |
| run | 고정된 5방식, P 공유 파생, 고정 재시도, 시간초과 우선, 모델 변경, 저장 실패, 중간 단계 강제 종료·원문 보존 |
| import-run / resolve-state | 실제 입력·모델·옵션, 미확인 입력 누락, 실패의 부당한 완료 전환, 원본 보존 |
| code / ai | 값·인용 검사, AI 항목별 실패, 전체 실패·시간초과, 기록 저장 실패 시 재시도 중단 |
| packets / import-review / finalize | 익명 입력, 두 사람 독립 판정, 추가 등록·중복 차단·구형 파일 보존, 이견·보류·감사 기록 |
| report / compare | 고정 분모·기사 가중·집계 재계산, 누락·미확정 차단, 전후 조건, 비용 출처·값·중단 부분합 |
| validate-judge | 원출력/점수 대조, 실패 포함 혼동표, 조정/검증 그룹 분리, 사람 최종 감사 |

이는 평가도구 전체 모듈과 명령 경로의 점검 범위입니다. 가능한 모든 입력 조합이나 모든 컴퓨터에서의 무결함을 증명하지는 않습니다.
같은 평가 폴더를 여러 담당자가 동시에 쓰지 않습니다. 중단된 생성 호출은 담당자 확인 전 재실행하지 않으며, 실제 AI 채점 정확도와 사람 검토의 독립성은 별도 검증합니다.
